# 压测方案与基线数据

所有限流/连接池阈值（Tomcat 80 线程、Hikari 20 连接、Nginx 40r/s）都是按公式推算的，
不是实测出来的。这份文档记录了怎么量、量什么，以及目前能拿到的基线。

脚本：`tools/loadtest.js`（零依赖，只用 Node 内置模块，Windows 可直接跑）。

## 一、为什么要分层测

优化效果必须能被拆开归因，混在一起测等于什么都没证明。三组独立变量：

| 组 | 变量 | 目的 |
| --- | --- | --- |
| A 基线 | 关闭缓存、关闭限流 | 系统吞吐的「地板」，即纯 Tomcat + MySQL 能力 |
| B 缓存 | 开启 Redis 缓存 | 量化缓存带来的吞吐倍数与 p99 改善 |
| C 限流 | 开启限流 + Nginx | 确认限流层的开销可以忽略，且 429 行为符合预期 |

只测 A 和 C、不测 B 的话，无法回答「缓存到底值多少钱」。

## 二、命令

```bash
# A 基线：无缓存、无限流
java -jar novel-service-1.0.0.jar \
  --reader.cache.enabled=false --rate-limit.enabled=false \
  --server.tomcat.threads.max=80 --server.tomcat.accept-count=100 \
  --spring.datasource.hikari.maximum-pool-size=20 \
  --spring.datasource.hikari.connection-timeout=3000

node tools/loadtest.js --url http://localhost:8080/front/books/home \
  --concurrency 50 --requests 3000

# B 缓存：保持 Redis 在线，其余同上，只把 reader.cache.enabled 设为 true
node tools/loadtest.js --url http://localhost:8080/front/books/home \
  --concurrency 50 --requests 3000

# C 限流：开启 rate-limit.enabled，验证被限流时的状态码与 Retry-After
node tools/loadtest.js --url http://localhost:8080/front/books/home \
  --concurrency 300 --requests 3000
```

单章节正文用 `/front/books/{bookId}/chapters/{chapterId}`，导入用 `curl` 单发计时（批处理场景不适合压 QPS）。

## 三、已测：A 基线（无缓存、无限流）

环境：Windows 11 / JDK 17.0.18 / MySQL 8 本机 / 应用与压测脚本同机。
数据量：`book_info` 为示例数据（数十行），首页每次请求 3 条 SELECT。
Redis 未启动，因此缓存与限流两列均未参与。

| 并发 | 吞吐 | p50 | p90 | p99 | 失败 |
| --- | --- | --- | --- | --- | --- |
| 50 | 1074 req/s | 32.8 ms | 48.2 ms | 748.1 ms | 0 |
| 200 | 2214 req/s | 70.1 ms | 142.2 ms | 238.7 ms | 0 |

两个值得注意的现象：

1. **并发 200 的吞吐反而高于 50**：压测脚本与 JVM 同机，50 并发时客户端自己先成了瓶颈；
   真正的服务端容量要看 200 并发那组。
2. **并发 50 的 p99 是 748ms，远高于 200 并发时的 239ms**：50 并发下排队更久，
   是 Hikari 20 连接 + 3 次串行查询造成的等待，不是 GC 或锁。

## 五、读数注意事项

- **必须关掉前置的 Nginx 限流**，否则测的是 Nginx 不是应用；测限流层时再单独打开。
- **先预热**：缓存开启时先打 100 次把 key 填好，再开始计时，否则测的是冷启动。
- **HTTP 200 不等于成功**：本项目的全局异常处理器会把部分错误包成 200 + body 里的 code，
  所以脚本额外统计「body 里没有 `"code":"00000"`」的业务失败数。
- **同机压测有上限**：客户端、JVM、MySQL 抢同一块 CPU 和同一张网卡，绝对值偏低；
  看趋势和相对倍数比看绝对值可靠。
