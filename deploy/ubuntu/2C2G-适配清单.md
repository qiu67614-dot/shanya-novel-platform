# 2 vCPU / 2 GiB 实例适配清单

适用于 `ecs.e-c1m1.large`（2 vCPU、2 GiB、ESSD Entry 40 GiB）这类入门实例。仓库里的默认参数原本是按 4C8G 推算的，直接搬过去会在运行第一天就出问题，本文列出必须调整的全部项目。

**在 8 GiB 及以上实例部署时，本文可以整篇跳过。**

## 一、内存预算

2 GiB 是所有进程共享的总量，先看清楚这笔账：

| 进程 | 常驻内存 | 说明 |
| --- | --- | --- |
| JVM（`-Xmx512m`） | ~750 MB | 堆 512 + Metaspace 192 + 线程栈 + 直接内存 |
| MySQL 8.0（调参后） | ~400 MB | 默认配置要 700~900 MB |
| Redis | ~30 MB | 只有限流计数和验证码 |
| Nginx | ~20 MB | 静态文件 + 反代 |
| Ubuntu 24.04 基础系统 | ~200 MB | systemd、sshd、snapd |
| **合计** | **~1.4 GB** | 剩 600 MB 做页缓存 |

余量很薄，所以下面四项不是「建议」，是必须。

## 二、必须做的四项

### 1. JVM 堆降到 512 MB（已在仓库改好）

`novel.service` 的 `ExecStart` 现为 `-Xms256m -Xmx512m -XX:MaxMetaspaceSize=192m`。

原来是 `-Xmx1536m`，那是 4C8G 的取值。在 2 GiB 机器上，JVM 会先占住 1.5 GB，MySQL 启动时内存不够，**OOM killer 会挑最大的进程杀掉**——通常就是 mysqld。表现是「网站突然全站 500，重启 MySQL 又好」，而且日志里只有一行 `Out of memory: Killed process`，很容易误判成数据库崩溃。

### 2. 线程池与连接池下调（已在仓库改好）

`application-prod.yml`：

| 参数 | 原值 | 现值 | 依据 |
| --- | --- | --- | --- |
| `tomcat.threads.max` | 80 | 40 | 2 核上 80 线程只会增加上下文切换 |
| `tomcat.threads.min-spare` | 10 | 8 | 同上 |
| `tomcat.accept-count` | 100 | 60 | 队列比工作线程还长没有意义 |
| `tomcat.max-connections` | 1000 | 500 | 单机不需要支撑千连接 |
| `hikari.maximum-pool-size` | 20 | 12 | 本机 MySQL，每条连接都有服务端开销 |
| `hikari.minimum-idle` | 20 | 12 | 保持固定池 |

换成 8 GiB 或改用 RDS 后，这些值可以整体回调（注释里写了目标值）。

### 3. MySQL 调参（新增 `mysql-2c2g.cnf`）

```bash
sudo install -m 0644 mysql-2c2g.cnf /etc/mysql/mysql.conf.d/zz-novel-2c2g.cnf
sudo systemctl restart mysql
```

核心三条：`innodb_buffer_pool_size=256M`、`performance_schema=OFF`（省 150~200 MB）、`mysqlx=OFF`。完整内容见文件内注释。

关掉 `performance_schema` 会失去 `performance_schema` 库里的细粒度统计，但慢查询日志仍然保留，排查够用。

### 4. 加 2 GB swap（这一步在服务器上做）

不是为了提高速度，是为了**把「进程被杀」变成「短暂变慢」**：

```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
# 降低换出倾向：只在真正吃紧时才用 swap
echo 'vm.swappiness=10' | sudo tee /etc/sysctl.d/99-novel-swap.conf
sudo sysctl --system
free -h
```

`free -h` 应能看到 2.0Gi 的 Swap。**不要**把 swappiness 设成 0，那样内核几乎不用 swap，等于没加。

## 三、带宽：把 1 Mbps 调大

购买页默认峰值 1 Mbps，等于是 128 KB/s。两个直接后果：

- 管理端主包 gzip 后 375 KB，下载要 3 秒，首屏十几秒
- 用户上传 20 MB 的 TXT，要 160 秒

「按使用流量」计费下，**带宽峰值不额外收费，只按实际流量（¥0.8/GB）结算**。所以买到 5~10 Mbps 是零成本的，控制台改一下即可：

> ECS 控制台 → 实例 → 更多 → 网络和安全组 → 修改带宽 → 峰值带宽改为 10 Mbps（计费方式不变）

按每月 10 GB 出网流量估算，账单约 ¥8。

## 四、这台机器不适合做的事

- **跑 200 并发压测然后写进简历**。`ecs.e` 是共享型实例，CPU 受同宿主邻居影响，数据不可复现。压测在本地机器做，这台只用来验证「最低配能跑」。
- **在本机存数据库备份**。40 GB 系统盘，MySQL 数据 + binlog 就会占掉几 GB，备份必须走 OSS（`novel-backup.sh` 已经是这个设计）。
- **开 binlog 长保留**。已设为 3 天，够回滚误操作，再长会把盘写满。
- **同机再跑别的服务**。Java + MySQL + Redis 已经吃掉 1.4 GB，加一个 Node 应用就会开始 swap。

## 五、验收

部署完成后逐条确认：

```bash
free -h                                    # Swap 2.0Gi 已生效；available 应 > 400 Mi
ps -o rss= -C java | awk '{print $1/1024" MB"}'   # JVM 常驻 700~800 MB 属正常
mysqladmin -p status | head -1             # 确认 MySQL 正常
curl -s -o /dev/null -w "%{time_total}\n" https://你的域名/api/front/books/home   # 首字节 < 1s
curl -s -o /dev/null -w "%{speed_download}\n" https://你的域名/js/chunk-vendors.*.js  # 下载速度应接近带宽上限
sudo journalctl -u novel --since "10 min ago" | grep -i "out of memory\|killed"     # 无输出
```

如果 `free -h` 的 available 长期低于 200 MB，说明某项配置没生效——大概率是 MySQL 调参文件没被加载（用 `mysql -e "SHOW VARIABLES LIKE 'innodb_buffer_pool_size'"` 核对，应为 268435456）。
